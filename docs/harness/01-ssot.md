## 2. Protected 보호 경계와 권한

Protected 보호 경로는 사람이 소유하는 정책·지침 영역이다.

- `docs/01-requirements.md`
- `docs/06-architecture.md`
- `docs/harness/`
- `AGENTS.md`
- `CLAUDE.md`

애플리케이션 코드와 Issue별 테스트는 Issue 범위 안에서 AI가 수정할 수 있다. 위 보호 경로를 변경해야 할 때 AI는 사람에게 대상 경로·필요성·변경 범위를 보고하고, 사람이 명시적으로 지시한 범위 안에서만 작업한다. AI가 보호 경로를 임의로 추가·확정하거나 범위를 넓혀서는 안 된다.

사람의 명시적 지시는 **수정 허용 범위**이지 최종 CI 승인 자체가 아니다. 보호 경로 변경을 통과하려면 사람이 변경 내용을 직접 검토하고 GitHub PR에 현재 source head를 대상으로 승인 리뷰를 남겨야 한다.

## 3. 사람 승인과 Protected 판정

CI와 로컬의 Protected는 동일한 규칙을 적용한다.

- 보호 경로 변경이 없으면 승인 없이 통과한다.
- 보호 경로 변경이 있으면 열린 GitHub PR이 필요하다.
- PR의 변경 범위에 포함된 보호 파일만 `Protected-Scope: <경로[,경로...]>` 형식으로 승인 리뷰 본문에 명시해야 한다. 범위는 실제 보호 변경을 모두 포함해야 하며 보호 경로 밖의 경로는 승인 범위로 허용하지 않는다.
- 승인 리뷰는 현재 source head 커밋에 연결되어야 한다. head가 바뀌면 재승인해야 한다.
- 승인자는 GitHub가 `User`로 식별하는 지정된 사람이어야 하며, 봇·GitHub App·AI·자동화 계정은 인정하지 않는다. PR 작성자 자기 승인은 인정하지 않는다.
- 승인 리뷰의 최신 상태가 `APPROVED`가 아니거나, 승인자·commit·범위 정보를 확인할 수 없으면 통과시키지 않는다.
- 사람이 직접 남긴 승인 리뷰는 사람의 명시적 지시와 별개의 최종 승인 기록이다. AI와 CI는 승인 리뷰나 승인 범위를 생성·수정·대체할 수 없다.
- 자연어 지시, PR 제목·본문·라벨, 커밋 메시지만으로 사람의 지시나 승인을 추론하지 않는다. 명시적 범위 또는 승인 정보를 확인할 수 없으면 `NEEDS_HUMAN`이다.
- PR·리뷰 상태를 확인할 수 없거나 정책 적용 여부가 불명확하면 fail-closed로 `NEEDS_HUMAN`에 머문다.

GitHub 계정이 실제로 사람이 직접 조작했는지 소프트웨어만으로 증명할 수는 없다. 따라서 Protected가 검증하는 사람성은 조직에서 지정한 `User` 계정이라는 기계적으로 확인 가능한 조건이며, 더 강한 신원 보장은 GitHub 조직·저장소 설정의 책임이다.

## 4. 충돌 처리와 보호 경계

1. 참고 문서와 SSOT가 충돌하면 SSOT를 우선한다.
2. GitHub Issue와 SSOT가 충돌하면 `NEEDS_HUMAN`을 선언하고 사람에게 판단을 요청한다.
3. SSOT와 SSOT가 충돌해도 `NEEDS_HUMAN`을 선언하고 사람에게 판단을 요청한다.
4. 충돌 범위에서 AI는 자신의 판단대로 구현·문서 수정·데이터 변경·완료 선언을 하지 않는다.
5. 사람이 SSOT 수정을 명시적으로 요청하면 요청된 범위 안에서만 반영하고, 요청에 없는 정책·예외·우선순위는 추가하지 않는다.
6. Issue 범위를 넘어서는 수정이 필요하면 범위 확대를 요청하고 그 전까지 보류한다.

`NEEDS_HUMAN` 보고에는 충돌한 원본과 위치, 각 주장, 영향 범위, 사람에게 필요한 결정, 결정 전 보류할 행동을 포함한다.

## 5. 원본 변경 원칙

- 한 책임의 규칙은 해당 SSOT에만 기록한다. 다른 문서에는 복제하지 말고 링크한다.
- 도메인 정책은 SSOT 1, 기술 경계는 SSOT 2, 하네스 실행·실패 처리는 SSOT 3, 작업 범위는 SSOT 4가 소유한다.
- 원본이 없거나 충돌이 해소되지 않으면 임의로 보완하지 않고 `NEEDS_HUMAN`, `미정`, `확인 필요` 중 적절한 상태로 보고한다.
- 보호정책 자체의 변경은 이 문서와 실행 계약·판정 구현을 함께 정합화하고, 사람의 검토와 승인을 거친다.

## 6. 구현 루프 기본값

유지보수 Issue의 구현 루프 최대 횟수 기본값은 **3회**다. 구현·검증·수정 반복이 3회 안에 종료 조건을 충족하지 못하면 AI는 반복을 계속하지 않고 `NEEDS_HUMAN`으로 전환한다. 보호 경로 승인 부족이나 SSOT 충돌은 자동 재시도하지 않고 즉시 사람에게 넘긴다.

## 7. 상태 표기

| 상태 | 의미 |
|---|---|
| `NEEDS_HUMAN` | Issue↔SSOT 또는 SSOT↔SSOT 충돌, 승인·범위·신원 확인 불가. 사람 판단 전까지 보류 |
| `추후 생성` | 아직 원본·스크립트·절차가 없음 |
| `Issue 미지정` | 작업 계약이 될 Issue가 없음 |
| `미구현` | 요구사항 또는 계획에는 있으나 구현되지 않음 |
| `없음(정상)` | 현재 등록 대상이 없는 정상 상태 |
