# 03. Issue 작업·PR Gate 반복 절차

> 이 문서는 하나의 GitHub Issue 작업 단위가 시작되어 완료 또는 `NEEDS_HUMAN`으로 끝날 때까지의 절차를 정의한다. 검증 단계와 기계 판정은 [`02-verification.md`](02-verification.md), 원본·보호 경계와 충돌 원칙은 [`01-ssot.md`](01-ssot.md)가 소유한다.

## 1. 전체 흐름

```text
┌────────────────────────────────────────────────────────────┐
│                    하나의 Issue 작업 단위                  │
└────────────────────────────────────────────────────────────┘
              │
              ▼
┌──────────────────┐     계약 누락·충돌·판정 불가     ┌─────────────────┐
│ 1. Issue 계약 확인 │ ─────────────────────────────▶ │ NEEDS_HUMAN     │
│ 범위·종료·TRY 확인 │                                 │ 결정 전 작업 중단 │
└────────┬─────────┘                                 └───────┬─────────┘
         │ 유효                                             │ 사람 결정
         ▼                                                   ▼
┌──────────────────┐                               ┌─────────────────┐
│ 2. 상태 인계 확인  │ ◀──────────────────────────── │ 결정 기록·재개점   │
│ Issue/branch/PR   │                               └─────────────────┘
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. TRY 시작       │  구현 또는 수정 + Local Verify 1회
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. Issue 범위 구현 │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. Local Verify   │ ──▶ 02-verification 판정
└────────┬─────────┘
         │
    ┌────┼──────────────┐
    ▼    ▼              ▼
  PASS  일반 FAIL    NEEDS_HUMAN
    │    │              │
    │    │ TRY 소진     │ TRY 미소진
    │    ▼              ▼
    │  남은 TRY?     사람 결정 전 정지
    │  ├─ 있음: 재구현
    │  └─ 없음: NEEDS_HUMAN
    ▼
┌──────────────────┐
│ 6. 종료 조건 확인  │
└────────┬─────────┘
         ├─ 미충족 → 다음 TRY
         └─ 충족
              ▼
┌──────────────────┐
│ 7. PR Gate         │
│ PR → CI → LLM     │
│ Review → 사람 판단 │
└────────┬─────────┘
         ├─ 반려/구현 오류 → 기존 Issue·PR의 구현 단계로 복귀
         └─ 승인 → 사람이 Merge
```

## 2. 단계와 담당

| 단계 | 담당 | 결과 |
|---|---|---|
| Issue 계약 | Issue 템플릿·GitHub Issue | 범위·종료 조건·최대 TRY 확정 |
| 구현 | 구현 에이전트 | Issue 범위 내 변경 |
| Local Verify | `02-verification.md` | 기계 검증 판정 |
| 반복 처리 | 이 문서 | 재구현·중단·재개 결정 |
| CI | GitHub Actions | Local Verify 재실행 결과 |
| LLM Review | 독립 리뷰 에이전트 | 의견 기록(최종 승인 아님) |
| 사람 판단 | 사람/PM | 승인·반려·정책 결정 |
| Merge | 사람 | 최종 반영 |

구현 에이전트와 LLM Review 에이전트는 분리한다. LLM Review는 diff·구조·위험을 검토해 의견을 남기지만 승인·반려·Merge를 대신하지 않는다.

## 3. 작업 시작

구현 전 다음을 확인한다.

1. GitHub Issue가 SSOT 4 작업 계약인지 확인한다.
2. Issue의 변경 범위·비범위·종료 조건·기계 검증을 읽는다.
3. Issue 템플릿의 `구현 루프 최대 횟수`를 읽는다.
4. 관련 SSOT와 충돌하는지 확인한다.
5. 현재 Issue 전용 branch와 PR을 확인한다.
6. 이전 TRY와 사람 판단 대기 기록을 확인한다.

계약·범위·최대 TRY가 없거나 서로 충돌하면 구현하지 않고 `NEEDS_HUMAN`으로 보류한다. SSOT 3의 기본 TRY는 3회지만, Issue에 작업별 값이 있으면 그 값을 사용한다.

## 4. TRY 정의와 횟수

### 4.1 한 TRY

한 TRY는 다음 묶음이다.

```text
Issue 계약·상태 확인
→ Issue 범위 구현 또는 수정
→ Local `npm run verify` 1회 완료
→ 02 판정 결과 기록
```

- TRY는 구현 변경과 그 변경의 Local Verify를 기준으로 센다.
- 같은 변경 상태에서 `npm run verify`를 다시 실행하는 것은 같은 TRY다.
- 로그 확인·단순 재실행·동일 원인의 환경 재현은 새 TRY가 아니다.
- CI 재실행, LLM Review, 사람 승인·반려 대기는 Local TRY에 포함하지 않는다.
- 일반 검증 실패를 수정한 뒤 재검증할 때 다음 TRY를 사용한다.
- 성공하면 즉시 작업 단위를 종료하고 남은 TRY를 사용하지 않는다.

### 4.2 상한

- 전역 기본값: 3회 (`01-ssot.md`)
- 작업별 상한: GitHub Issue의 `구현 루프 최대 횟수`
- 허용값: Issue 템플릿에 정의된 선택값
- 상한에 도달한 일반 실패: 추가 자동 수정을 하지 않고 `NEEDS_HUMAN`
- TRY 번호는 감소·초기화하지 않는다. 사람이 새 요구 또는 새 작업 계약을 명시한 경우에만 새 작업 단위로 시작한다.

## 5. Local Verify 판정 후 반복

### PASS

1. Issue의 모든 종료 조건을 다시 확인한다.
2. 조건이 모두 충족되면 완료 기록을 남긴다.
3. PR Gate로 이동한다.
4. 조건이 충족되지 않으면 부족한 조건을 수정하는 다음 TRY로 이동한다.

### 일반 FAIL

Types, Lint, Architecture Check, Test, Build 또는 Issue 기계 검증 실패 중 Issue 범위 안에서 원인을 수정할 수 있는 경우:

```text
실패 단계·출력 기록
→ 현재 TRY 소진
→ 남은 TRY 확인
→ 다음 TRY에서 원인 수정
→ npm run verify
```

### NEEDS_HUMAN

다음은 TRY를 소진하지 않고 즉시 멈춘다.

- SSOT와 Issue 또는 SSOT끼리 충돌
- Protected 경로 수정·승인·범위 판단 필요
- Issue 범위 밖 변경 필요
- 요구사항·정책·아키텍처 의미를 사람이 결정해야 함
- Issue의 종료 조건·최대 TRY·금지 범위가 모호함
- 검증 규칙만으로 결과를 판정할 수 없음
- 환경·도구 오류로 판정 결과를 신뢰할 수 없음
- 이전 세션의 상태·사람 결정을 복구할 수 없음

사람 결정 전에는 수정·추가 검증·범위 확대·TRY 초기화를 하지 않는다.

## 6. PR Gate

로컬에서 다음 조건을 모두 충족해야 PR을 생성할 수 있다.

```text
마지막 Local Verify PASS
+ Issue 종료 조건 모두 충족
+ 필요한 완료 기록
```

PR 단계는 다음 절차로 진행한다.

```text
PR 생성/갱신
→ CI에서 동일한 verify 실행
→ 독립 LLM Review 의견 기록
→ 사람 최종 검토
→ 승인: 사람이 Merge
→ 반려: 기존 Issue·PR 구현 단계로 복귀
```

- CI는 Local Verify를 대체하지 않고 같은 검증을 다시 수행한다.
- CI가 실패하고 같은 원인이 로컬에서 확인되면 기존 작업 단위의 일반 FAIL 절차로 돌아간다.
- CI 실패 원인을 로컬에서 확인할 수 없으면 추측하지 않고 `NEEDS_HUMAN`으로 둔다.
- LLM Review 결과는 의견 기록이며 사람의 승인·반려를 대신하지 않는다.
- 사람은 기계 결과와 별개로 사용자에게 전달되는 의미, 도메인 의도, 표현의 적절성, 화면 혼동 가능성을 판단한다.
- 사람이 Merge하는 것이 최종 반영이다. AI는 Merge하지 않는다.

### 사람 반려

사람의 반려 기록을 받은 경우:

1. 이전 TRY 기록과 반려 사유를 보존한다.
2. 기존 Issue 계약의 구현 오류인지 새 요구사항인지 구분한다.
3. 기존 계약의 명시적 재작업이면 같은 Issue·PR의 구현 단계로 돌아간다.
4. 새 요구·범위 변경이면 Issue 계약과 필요한 원본을 먼저 갱신한다.
5. 반려 내용이 모호하면 질문하고 답변 전 수정하지 않는다.

사람 반려로 TRY를 1로 다시 세는 것은 사람의 명시적 결정과 기록이 있을 때만 적용한다. 자동으로 기록을 삭제하거나 카운터를 초기화하지 않는다.

## 7. 상태와 세션 인계

새 에이전트·새 세션은 구현 전에 다음을 복구한다.

```text
Issue / branch / PR
Issue 최대 TRY
현재 TRY 번호와 단계
마지막 Local Verify 판정·실패 단계·SHA
CI 결과
LLM Review 의견
사람 승인·반려·대기 상태
다음 허용 행동
```

상태가 없거나 서로 다른 Issue·branch·PR·SHA를 가리키면 새 TRY를 시작하지 않고 `NEEDS_HUMAN`으로 보류한다. 사람 판단 대기 중에는 해당 사유에 의존하는 변경을 하지 않는다.

권장 TRY 기록:

```text
Try: <현재>/<최대>
Issue: #<번호>
Branch: <branch>
PR: #<번호 또는 없음>
Head: <sha>
Local-Verify: PASS | FAIL | NEEDS_HUMAN
Failed-Stage: <단계 또는 없음>
LLM-Review: 기록됨 | 해당 없음
Human-Decision: 대기 | 승인 | 반려
Next: <다음 행동>
```

현재 저장소에는 이 기록을 자동 생성·복구하는 전용 실행기가 없으므로, Issue/PR과 인계 기록에 남긴다. 자동화가 도입되기 전까지 기록이 없으면 완료·재개를 추측하지 않는다.

## 8. 완료·중단

완료:

```text
Local Verify PASS
→ Issue 종료 조건 충족
→ PR Gate CI PASS
→ LLM Review 의견 기록
→ 사람 승인
→ 사람이 Merge
```

중단:

```text
사람 판단 필요 또는 최대 TRY 도달 또는 상태 복구 불가
→ NEEDS_HUMAN
→ 질문·영향·금지 행동·재개 단계 기록
→ 사람 결정 전 정지
```

## 9. 성숙도 점검

현재 작업 단위는 다음 축으로 점검한다.

- 계약: Issue 종료 조건
- 기준: SSOT
- 검증: Local Verify와 CI
- 경계: Protected
- 루프: 일반 실패·중단·재진입
- 기록: TRY·판정·사람 결정 인계
- 재사용: 향후 `issue-loop` Skill

현재 `issue-loop` Skill과 자동 TRY 저장은 미구현이면 미구현으로 보고한다. 이벤트 Hook, 예약 실행, 병렬 오케스트레이션, 비용 자동화는 필요가 확인된 뒤 별도 범위로 다룬다.
