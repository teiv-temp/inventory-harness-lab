# 03. 구현·검증 반복 절차

> 이 문서는 `02-verification.md`의 판정 결과 이후 로컬 구현·수정·재검증 절차를 정의한다. 검증 단계와 판정은 [`02-verification.md`](02-verification.md), SSOT와 보호 경계는 [`01-ssot.md`](01-ssot.md)가 소유한다.

## 1. 책임과 범위

이 문서는 하나의 Issue 작업에서 구현과 로컬 검증을 반복하는 방법을 정한다.

- 구현 변경과 로컬 검증을 하나의 시도로 묶는다.
- `02-verification.md`의 판정을 받아 다음 행동을 결정한다.
- 일반 실패는 수정 후 다시 검증한다.
- 사람이 판단해야 하는 상태는 `NEEDS_HUMAN`으로 멈춘다.
- 최대 시도 횟수와 현재 상태를 Issue 기록으로 남겨 세션이 바뀌어도 재진입한다.

이 문서는 검증 단계의 내용·게이트 기준·제품 요구사항·아키텍처·Protected 승인 절차·PR/CI/merge 운영을 정의하지 않는다. PR 이후 절차는 별도의 원본이 정해질 때까지 이 문서의 범위가 아니다.

## 2. 한 번의 시도

한 번의 시도는 다음 단위다.

```text
Issue 종료 조건과 변경 범위 확인
→ Issue 범위 안에서 구현 또는 수정
→ npm run verify 1회 실행
→ 결과 기록
```

- `npm run verify` 실행 횟수가 아니라 구현 변경과 그 검증 묶음의 횟수를 센다.
- 동일한 변경 상태에서 검증을 다시 실행하는 것은 새 시도가 아니다.
- 구현 중 여러 파일을 수정해도 검증 전까지는 하나의 시도다.
- 검증을 실행하지 않은 채 중단한 구현은 시도로 완료하지 않는다. 단, 즉시 중단 조건은 §5를 따른다.
- 로컬 시도만 이 문서의 횟수에 포함한다. CI나 다른 검토의 실행 횟수는 이 문서에서 세지 않는다.

## 3. 최대 시도 횟수

- 실제 상한은 해당 유지보수 Issue의 `구현 루프 최대 횟수`다.
- Issue 템플릿의 선택값을 사용한다.
- Issue에 값이 없거나 읽을 수 없으면 기본값을 임의로 적용하지 않고 `NEEDS_HUMAN`으로 멈춘다.
- 저장소의 기본값은 **3회**다.
- 시도 번호는 1부터 시작하고 감소시키지 않는다.
- 마지막 허용 시도까지 일반 실패를 해결하지 못하면 추가 수정 없이 `NEEDS_HUMAN`으로 멈춘다.

## 4. 검증 결과에 따른 반복

`npm run verify`의 구체적인 판정은 `02-verification.md`를 따른다.

### PASS

```text
PASS
→ Issue 종료 조건 확인
→ 모두 충족하면 로컬 반복 종료
→ 하나라도 미충족이면 원인을 수정할 다음 시도
```

PASS는 검증 실행이 성공했다는 뜻이며, Issue 종료 조건 전체가 충족됐다는 뜻과 자동으로 같지 않다.

### 일반 FAIL

Types, Lint, Architecture Check, Test, Build 또는 Issue 종료 조건의 기계 검증이 실패하고 AI가 Issue 범위 안에서 원인을 수정할 수 있으면:

```text
실패 단계·결과 기록
→ 현재 시도 1회 소진
→ 남은 횟수 확인
→ 다음 시도에서 수정
→ npm run verify
```

### 판정 불능 또는 사람 판단 필요

다음은 일반 실패로 반복하지 않는다.

- Issue와 SSOT 또는 SSOT끼리 충돌
- Protected 경로의 수정·승인 판단 필요
- Issue 범위 밖 변경 필요
- 제품 의미·정책·아키텍처 선택 필요
- Issue의 범위·종료 조건·최대 횟수가 모호함
- 검증 규칙만으로 결과를 결정할 수 없음
- 환경·도구 오류로 검증 결과를 신뢰할 수 없음
- 이전 시도나 사람의 결정을 복구할 수 없음

이 경우 `NEEDS_HUMAN`으로 멈춘다. 사람 결정 전에는 관련 코드 수정, 검증 재실행, 범위 확대, 횟수 초기화를 하지 않는다.

## 5. 상태 전이

```text
NOT_STARTED
    │ 구현 시작
    ▼
IN_PROGRESS
    │ npm run verify
    ▼
VERIFYING
    ├─ PASS ───────────────▶ PASSED
    ├─ 일반 FAIL ──────────▶ FAILED(attempt 소진)
    │                              │
    │                              ├─ 남은 횟수 있음 → 다음 시도
    │                              └─ 상한 도달 → NEEDS_HUMAN
    └─ 판정 불능/사람 필요 ─▶ NEEDS_HUMAN(attempt 미소진)

NEEDS_HUMAN ── 사람 결정 후 ──▶ 허용된 단계에서 재개
```

불변식:

- 같은 변경 상태의 검증 재실행은 시도를 중복 집계하지 않는다.
- 일반 FAIL은 시도를 소진한다.
- 사람 판단 대기는 시도를 소진하지 않는다.
- 시도 횟수는 감소·임의 초기화하지 않는다.
- `NEEDS_HUMAN`에서 사람 결정 없이 재개하지 않는다.
- 사람이 요구사항이나 범위를 변경하면 Issue 계약을 먼저 갱신한다.

## 6. 사람 판단과 `NEEDS_HUMAN`

`NEEDS_HUMAN`은 자동 반복을 중단하고 사람의 결정을 기다리는 상태다. 다음 형식으로 Issue에 기록한다.

```text
상태: NEEDS_HUMAN
Issue: #<번호>
Try: <사용 횟수>/<최대 횟수>
현재 단계: <단계>
현재 결과: <판정 또는 중단 사유>
관련 원본: <파일·절·Issue>
영향: <결정에 따라 달라지는 작업>
질문: <사람이 답할 하나의 질문>
결정 전 금지: <수정·검증·범위 확대 등>
결정 후 재개: <재개할 단계>
```

사람에게 요청해야 하는 판단은 가능한 한 하나의 질문으로 좁힌다. AI는 사람의 결정을 대신 해석하거나 승인·반려를 기록하지 않는다.

## 7. Issue 기록과 세션 재진입

시도마다 Issue에 누적 기록을 남긴다. 이전 기록을 덮어쓰지 않는다.

```text
Try: <번호>/<최대>
Issue: #<번호>
Branch: <branch>
Commit: <검증 대상 SHA>
Verify: npm run verify
Result: PASS | FAIL | NEEDS_HUMAN
Failed-Stage: <단계 또는 없음>
Consumes-Try: yes | no
Next: <다음 행동>
```

새 세션이나 새 에이전트는 구현 전에 최신 기록을 읽고 다음을 복구한다.

- Issue와 종료 조건
- 최대 시도 횟수와 사용한 시도
- 현재 상태와 마지막 단계
- 마지막 검증 결과와 commit SHA
- 실패 단계와 원인
- 보류 중인 사람 판단
- 다음에 허용된 행동

최신 기록이 없거나 서로 다른 Issue·branch·commit을 가리키거나 상태가 모호하면 새 시도를 시작하지 않고 `NEEDS_HUMAN`으로 둔다.

현재 저장소에는 이 기록을 자동으로 생성하거나 시도 횟수를 기계적으로 강제하는 전용 실행기가 없다. 따라서 기록이 실제로 남아 있지 않은 경우 횟수를 추측해 복구하지 않는다. 상태 추적 자동화는 이 절차와 기록 형식을 사람 검토 후 별도로 구현한다.

## 8. 로컬 반복의 종료

다음 중 하나면 로컬 구현·검증 반복을 종료한다.

- `npm run verify`가 PASS이고 Issue 종료 조건을 모두 확인함
- 최대 시도 횟수에 도달함
- 사람 판단이 필요함
- 작업 상태를 신뢰할 수 없음

이 문서는 로컬 반복의 종료까지 다룬다. 로컬 반복이 정상적으로 끝나면 다음 단계인 PR로 인계할 수 있지만, PR 이후의 CI·Review·승인·merge 절차는 이 문서에서 정하지 않는다.
