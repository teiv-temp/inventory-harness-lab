# 프로젝트 SSOT

> 이 문서는 저장소의 기준 문서를 가리키는 **정본 인덱스**다. 요구사항·아키텍처의 상세 내용을 복제하지 않으며, 각 영역의 원본과 변경 추적 규칙을 선언한다.

## 0. SSOT와 보호 경계

### 0.1 SSOT의 목적

SSOT(Single Source of Truth)는 자료를 한곳에 모으는 개념이 아니라, **질문별 최종 판단 기준을 하나로 지정하는 원칙**이다.

원본이 지정되지 않은 상태에서는 같은 질문에 대해 요구사항 문서, 코드 주석, 작업 Issue가 서로 다른 결론을 낼 수 있다. 이때 AI는 자료 중 하나를 임의로 선택해 적용하지 않으며, 판단을 보류하고 충돌 또는 미확정 상태를 보고한다.

원본이 지정된 상태에서는 AI가 해당 원본을 먼저 읽고 판단한다. 보조 자료는 맥락·예시·현재 상태를 제공할 뿐 최종 판단을 바꾸지 못한다.

### 0.2 질문별 최종 판단 기준

질문을 먼저 분류한 뒤 해당 행의 **최종 판단 기준**만 적용한다.

| 질문 | 최종 판단 기준 | 보조 자료 | 보호 경계 |
|---|---|---|---|
| 재고 도메인 의미·업무 정책 | [`docs/01-requirements.md`](../01-requirements.md) | 시나리오·UX 문서 | 요구사항에 없는 정책을 임의로 추가하지 않음 |
| 재고 감소 규칙 | [`docs/01-requirements.md`](../01-requirements.md)의 최종 요구사항 | 코드 주석·작업 Issue | 출고 확정 시 차감. 보조 자료가 충돌하면 요구사항을 따름 |
| 기술·데이터·트랜잭션 구조 | [`docs/06-architecture.md`](../06-architecture.md) | 구현 상태·인계 문서 | 아키텍처 원본을 우회하는 구조를 임의로 확정하지 않음 |
| 개별 작업의 범위·수용 기준·상태 | 해당 GitHub Issue | PR·커밋·인계 문서 | Issue가 없으면 `Issue 미지정`; 작업 범위를 추론하지 않음 |
| 검증 규칙 | 추후 생성될 검증 스크립트 | 기존 계획·테스트 기록 | 현재 규칙을 새로 만들거나 기존 기록을 SSOT 규칙으로 승격하지 않음 |
| 구현·검증 루프 | 추후 생성될 절차 | 기존 계획·인계 문서 | 절차가 없으면 완료를 임의로 선언하지 않음 |

예를 들어 “재고 감소는 언제 발생하는가?”라는 질문의 최종 답은 **출고 확정 시 차감**이며, 이 판단은 `docs/01-requirements.md`에서 한다. 코드 주석이나 작업 Issue에 다른 설명이 있어도 보조 자료일 뿐이며, 충돌 시 요구사항 문서를 따른다.

### 0.3 충돌 처리 정책

충돌이 발생하면 반드시 충돌 상태를 선언하고, 아래 규칙만 적용한다.

1. **참고 문서와 SSOT가 충돌하면 SSOT를 우선한다.** 참고 문서·코드 주석·현재 구현·PR·커밋은 해당 책임의 SSOT를 덮어쓰지 못한다.
2. **GitHub Issue와 SSOT가 충돌하면 `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다.** Issue를 자동으로 우선하거나 SSOT를 자동으로 변경하지 않는다.
3. **SSOT와 SSOT가 충돌해도 `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다.** 어느 SSOT가 우선인지 AI가 결정하지 않는다.
4. **AI는 충돌이 발생한 상태에서 자신의 판단대로 행동하지 않는다.** 구현·문서 수정·데이터 변경·완료 선언을 중단하고 판단이 필요한 두 원본과 충돌 내용을 보고한다.
5. **사람이 SSOT 수정을 명시적으로 요청하면 해당 수정을 받아들인다.** 이 경우에도 AI가 임의로 내용을 정하지 않고, 사람의 요청에 포함된 변경 범위와 내용을 그대로 반영한다. 요청이 모호하거나 서로 충돌하면 다시 `NEEDS_HUMAN` 상태로 판단을 요청한다.

사람의 명시적인 SSOT 수정 요청은 충돌 상태에서의 AI 자의적 판단과 다르다. AI는 요청받은 범위 안에서 SSOT를 수정할 수 있다. 단, 요청에 없는 정책·예외·우선순위를 추론해 추가하지 않는다.

`NEEDS_HUMAN` 보고에는 최소한 다음을 포함한다.

```markdown
상태: NEEDS_HUMAN
충돌한 원본: <문서 또는 Issue>
사람에게 요청할 판단: <채택할 기준 또는 SSOT 수정 여부>
결정 전 조치: 충돌 범위의 구현·문서 수정·데이터 변경·완료 선언 보류
```

- 충돌한 원본과 해당 위치
- 각 원본의 주장
- 영향받는 작업 또는 보호 경계
- 사람에게 요청하는 결정
- 결정 전까지 중단하는 행동

### 0.4 보호 경계

다음 경계는 구현·문서 해석·AI 답변에서 임의로 변경하거나 우회하지 않는다.

- 재고 도메인 정책은 `docs/01-requirements.md`의 의미를 따른다.
- 기술·데이터·트랜잭션 구조는 `docs/06-architecture.md`의 제약을 따른다.
- 개별 작업은 해당 GitHub Issue에 기록된 범위와 수용 기준 안에서만 다룬다.
- 지정 원본과 보조 자료가 충돌하면 보조 자료로 원본을 덮어쓰지 않는다.
- 지정 원본이 없거나 원본 자체가 충돌하면 AI가 임의로 결론을 만들지 않고 `미정`, `충돌`, `확인 필요` 중 하나로 보고한다.
- 현재 구현이 요구사항과 다르면 구현 사실과 요구사항 기준을 분리해 기록한다. 코드의 현재 동작만으로 요구사항을 소급 변경하지 않는다.
- 검증 규칙과 구현·검증 루프는 생성 전까지 정의된 것으로 간주하지 않는다.

### 0.5 AI 판단 절차

도메인 정책, 아키텍처, 작업 범위에 영향을 주는 질문에는 다음 순서를 따른다.

1. 질문 유형을 분류한다.
2. 표의 최종 판단 기준을 확인한다.
3. 지정 원본을 먼저 읽고 결론을 찾는다.
4. 보조 자료는 맥락과 충돌 여부 확인에만 사용한다.
5. 충돌 시 지정 원본과 충돌 자료를 함께 밝히고 지정 원본을 적용한다.
6. 지정 원본이 없거나 해석할 수 없으면 임의로 선택하거나 작업을 진행하지 않고 확인을 요청한다.
7. 답변 또는 변경 제안에 최소한 `판단 기준`, `결론`, `충돌 여부`, `미확정 사항`을 남긴다.

## 4. 원본이 없는 영역

다음 항목은 현재 문서 또는 초기 문서 기준에서 독립적인 원본을 확인하지 못한 영역이다.

### 외부 업무·승인 원자료

- 실제 사용자 인터뷰·현장 관찰 기록
- 현행 재고 시트·업무 매뉴얼·팝업 정산 양식
- 풀필먼트 계약·SLA·실제 업체명과 담당자
- 법규·감사 근거
- 요구사항·디자인·아키텍처 승인자와 승인 기록

### 운영 원본

- 독립 운영 런북 또는 SOP
- 백업·복구 명령, 주기, 보존 기간, 무결성 확인, WAL 처리
- 배포·롤백·환경변수·비밀 관리
- 장애 대응·모니터링·알림·RTO/RPO
- 계정 발급·회수·비밀번호 재설정·권한 운영
- 감사 로그·개인정보·데이터 보존 및 정정 절차
- 풀필먼트·팝업 현장 업무 SOP

요구사항에 SQLite 백업 필요성은 있지만, 구체적인 백업·복구 절차의 원본은 없다. 원격 배포·외부 API·CSV·바코드·오프라인·세분화된 권한 등은 일부가 명시적인 Out of Scope이므로, 문서 누락과 의도적 제외를 구분한다.

### 검증 결과·결정 관리 원본

- 모든 DoD·QA 항목의 실행 결과와 승인 증적을 모은 단일 문서
- M7 전체(`/expiry`, `/history`, `/settings`, 조정·QA)의 완료 결과
- IME·긴 상품명·동시 출고·장애·복구의 검증 결과
- 검증 실행 환경·실행자·시각·재현 절차
- 결정 로그(ADR), 문서 상태·승인·버전 레지스트리
- 공통 용어집·정책 레지스트리

## 5. 우선순위와 변경 규칙

### 5.1 우선순위

1. **재고 도메인·업무 정책·완료 기준:** `docs/01-requirements.md`
2. **기술·데이터·트랜잭션 아키텍처:** `docs/06-architecture.md`
3. **개별 작업의 범위·수용 기준·상태:** 해당 GitHub Issue
4. **시나리오·UX·계획·현재 상태:** 각각의 보조 문서
5. **검증 규칙 및 구현·검증 루프:** 현재는 미정이며 추후 생성

여러 원본의 영역이 겹칠 때는 먼저 해당 결정이 도메인 정책인지, 기술 구조인지, 개별 작업 범위인지 구분한다. 영역을 임의로 넘겨서 해석하지 않는다.

### 5.2 변경 절차

- 도메인 정책 변경은 `docs/01-requirements.md`를 먼저 갱신하고, 영향을 받는 아키텍처·시나리오·작업 Issue를 연결한다.
- 아키텍처 변경은 `docs/06-architecture.md`를 먼저 갱신하고, 관련 도메인 요구사항과 작업 Issue를 연결한다.
- 개별 작업은 반드시 해당 GitHub Issue를 만든 뒤 Issue를 원본으로 삼는다. Issue가 없는 작업은 `Issue 미지정`으로 남기며, 이 SSOT가 작업 범위를 대신 정의하지 않는다.
- Issue가 요구사항 또는 아키텍처를 변경해야 한다면, Issue에서 변경 필요성을 기록하고 해당 권위 원본을 갱신한 뒤 구현한다. Issue만으로 원본 문서의 정책을 암묵적으로 덮어쓰지 않는다.
- Pull Request와 커밋은 변경 이력과 구현 결과를 제공하지만, 개별 작업의 원본인 GitHub Issue를 대체하지 않는다.
- 문서 간 충돌은 임의로 합치지 않는다. 충돌 당사자, 영향 범위, 해결된 원본과 Issue를 추후 결정 로그에 남긴다.

## 4. 현재 작업 추적

### GitHub Issues

현재 확인된 등록 Issue: **없음**.

따라서 현재 SSOT에는 연결할 개별 작업이 없다. 새 기능·버그·문서 작업을 시작할 때는 먼저 [GitHub Issue 목록](https://github.com/teiv-temp/inventory-harness-lab/issues)에 Issue를 등록하고, 이 표에 Issue 번호·제목·URL·상태를 추가한다.

| Issue | 제목 | 상태 | 범위·수용 기준 |
|---|---|---|---|
| 없음 | 등록된 작업 없음 | — | 추후 생성 |

> PR은 Issue가 아니다. 병합된 PR #1은 작업 결과의 이력이며, 이 표의 Issue 원본으로 등록하지 않는다.

### 미결·후속 작업

| 항목 | 원본 | 상태 |
|---|---|---|
| 개별 작업 목록 | 해당 GitHub Issue | Issue 미지정 |
| 검증 규칙 | 추후 생성될 검증 스크립트 | 추후 생성 |
| 구현·검증 루프 | 추후 정의될 절차 | 추후 생성 |
| 독립 운영 런북 | 현재 없음 | 추후 생성 여부 결정 |

## 5. 검증과 구현·검증 루프

### 검증 규칙

**추후 생성.** 검증 규칙은 향후 스크립트로 대체할 예정이므로, 현재 이 문서에서는 명령어·판정 기준·통과 조건·체크리스트를 정의하지 않는다.

### 구현·검증 루프

**추후 생성.** 작업 시작부터 Issue 연결, 구현, 검증, 결과 기록, 원본 문서 갱신까지의 반복 절차는 아직 정의하지 않는다.

검증 규칙이나 루프가 생성되면 이 섹션의 상태와 해당 원본 링크만 갱신한다. 이 문서에서 임의의 임시 규칙을 먼저 만들지 않는다.

## 6. 상태 및 빈 값 표기

충돌이 해소될 때까지 사용하는 보호 상태는 `NEEDS_HUMAN`이다. 이 상태에서는 AI가 구현, 문서 수정, 데이터 변경, 완료 선언을 진행하지 않는다.


상태가 비어 있는 것과 아직 결정되지 않은 것을 구분한다.

| 표기 | 의미 |
|---|---|
| `없음(정상)` | 해당 영역이 현재 범위에 없거나 등록 대상이 없음 |
| `추후 생성` | 향후 별도 원본·스크립트·절차를 만들 예정이며 현재는 정의하지 않음 |
| `Issue 미지정` | 작업 원본이 될 GitHub Issue가 아직 연결되지 않음 |
| `미구현` | 요구사항 또는 계획에는 있으나 현재 구현 상태가 완료되지 않음 |
| `미정` | 결정 자체가 아직 내려지지 않음 |

빈 목록을 숨기지 않는다. 등록된 항목이 없으면 `등록된 작업 없음`처럼 표시하고, 필요한 다음 조치를 함께 적는다.

## 7. 기준 문서와 실제 상태의 구분

- `docs/01-requirements.md`는 재고 도메인 정책과 완료 기준의 원본이다.
- `docs/06-architecture.md`는 기술·데이터·트랜잭션 구조의 원본이다.
- `docs/07-plan.md`는 기존 계획을 보여주지만, 새 검증 규칙의 원본이 아니다.
- `docs/HANDOVER.md`는 특정 시점의 현재 상태·검증 결과·인계 기록이며, 요구사항이나 아키텍처를 자동으로 변경하지 않는다.
- `README.md`는 실행 안내이며 정책의 원본이 아니다.
- GitHub Issue는 해당 작업의 범위·수용 기준·상태를 다루며, 도메인·아키텍처 원본을 대체하지 않는다.
