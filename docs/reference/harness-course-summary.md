## 1. 하네스란 무엇인가 (≈p.6~9)

- 하네스 = 규칙 파일 + 도구 권한 제한 + 테스트·Hook·CI로 품질을 지키는 **통제 인프라**
- 프롬프트와의 차이: "좋은 답을 부탁하는 문장"(설명으로 유도, 모델 자기판단 의존, 1회성 성공)이 아니라 "**좋은 결과가 아니면 통과하지 못하게 만드는 환경**"(실행 결과와 권한으로 제한, 세션이 바뀌어도 유지, 반복 가능한 성공과 안전한 실패)
- **초기 구축 순서의 함정**: 기준·규칙·경계·CI를 전부 선구축 후 업무 투입하면, 직접 확인하지 않은 업무 규칙은 추측에 불과하고 **보지 못한 실패는 막을 수 없다**
- 실제 제작 과정 = 개선 루프: 규칙 없이 먼저 실행 → 실패 관찰 → 원인 분류(규칙 문제 vs 집행 문제) → 보완 → 재검증
- 2일차 목표: **이 루프를 에이전트가 돌리고 사람은 판단만 하는 것**

### 자율 루프의 최소 구조

계약 → 실행 → 기계 검증 → 독립 검증 → 사람 판단

### 사람의 권한으로 남는 5구간

| 구간 | 내용 |
|---|---|
| 계약 확정 | Issue의 의도와 종료 조건 |
| 화면 확인 | 실제 화면 ↔ 업무 의도 일치 |
| 정책 변경 | 보호 문서·하네스 규칙 변경 |
| 최종 승인 | 승인 전 Merge 금지 |
| 충돌·정보 부족 | 해결할 수 없는 판단은 사람에게 넘긴다 |

## 2. 유지보수 대상 경계 (실습 B1, ≈p.30~34)

출발점 질문 3개 — Q1 무엇을 유지보수하나(대상 없으면 계약·검증 실체 없음) / Q2 정상 동작은 무엇인가(기준선 없으면 회귀 판정 불가) / Q3 잘못 고치면 무엇이 깨지나(영향 경로 없으면 보호 경계 불가)

- inventory-poc: 거점별 재고(자사창고·풀필먼트·팝업), 가용/출고가능/전체 재고 구분, Lot·FEFO, Prisma+SQLite 시드
- 발견 결함 3유형("숫자가 안 맞는다"): 합계 어긋남 / 명칭 어긋남(가용 vs 출고가능) / FEFO 아닌 Lot 차감

## 3. B5. Issue 계약서와 종료 조건 (≈p.85)

|---|---|---|

| 5 | 건드리면 안 되는 것 | 변경 경계는 어디인가 |
| 6 | 구현 루프 최대 횟수 | 몇 번까지 재시도하는가 |

## 4. A7. 재시도 상한과 시도 기록

- 시도 기록: 작업 시작 시 Issue comment 1건 추가. **덮어쓰지 않고 누적**, 숫자 갱신이 아니라 **개수 세기로 복구**
- loop 필드로 로컬 구현 루프 / CI 수정 루프를 구분
- 세션이 끊겨도 다음 에이전트가 Issue comment를 읽고 상태 복구 — Issue 하나면 충분

## 5. NEEDS-HUMAN — 안전한 중단

진입 조건 3가지:
1. **계약 충돌** — Issue의 전제와 SSOT·현재 동작이 어긋남
2. **정보 부족** — 판단에 필요한 값이 없고 빈칸을 채울 근거도 없음
3. **상한 초과** — 정한 한도를 넘겨 같은 실패 반복

원칙: **정보가 없으면 빈칸을 임의로 채우지 않는다.** 멈추고 사람에게 필요한 정보를 요청한다.
사람 판단 3갈래는 모두 정상 경로(중단 뒤 방치 방지). 전제가 틀린 테스트는 제거한다 — 잘못된 테스트는 코드보다 오래 남는다.

## 6. A8/B8. PR Gate — 승인·반려 루프 (≈p.110~117)

정의된 공백: Local Verify PASS 이후 규칙 부재 — PR 생성 조건 · 재검증 범위 · LLM Review 시점과 담당 · 승인 주체

- **PASS는 Merge 허가가 아니다** — 계약 충족 ≠ 의도 충족. 화면 명칭·안내 문구는 기계 판정 밖에 있다
- 기계/사람 판단 구분 — 숫자·형식·테스트 통과 = 기계(AI) / 사용자에게 전달되는 의미 구조·도메인 의도의 적절성·diff의 잠재 위험·계약과 실제 의도의 일치 = 사람
- **LLM Review는 승인·반려를 결정하지 않는다.** 최종 승인·반려·Merge는 사람
- 반려 후 복귀 지점 = PR이 아닌 **구현 단계**: 같은 Issue·같은 Branch·같은 PR 유지, TRY 기록 보존, 이전 PASS는 무효(npm run verify 처음부터)
- 계약 변경 ≠ 재작업: 종료 조건 안의 구현 오류 → 같은 PR 재검증 / 종료 조건·SSOT 자체 변경 → 사람 승인 후 Issue·SSOT 갱신하는 별도 경로

## 7. A9/B9. issue-loop Skill

- 자연어("이슈 처리해줘") → skill-creator로 실행 구조화. 하네스 문서가 입력 재료, 세부 조건은 원본 대조 후 확정
- 발동 조건 정밀화: "항상 확인" → "필요할 때만 확인"
- 중복 재질문 제거: 새 정책을 Skill에 만들지 않고 **원본 기본값(최대 3회)** 사용 — 빈칸은 추측이 아닌 원본 기본값 처리
- 구현과 리뷰 맥락 분리: PASS 이후 독립 reviewer, diff·하네스 기준 중심 검토, 결과는 PR 코멘트로 기록
- AGENTS.md 경로 분기: 요청 시 Skill 사용 여부를 사람에게 확인 → 자동(Skill 10단계)/수동(하네스 문서 따라 진행), 둘 다 사람 최종 판단 직전에 중단
- 수정 대상 선택: 기준의 공백 = 원본 수정 / Skill 해석 오류 = Skill 수정 / 편의를 위한 순서 설명 = Skill 작성 / 새 운영 정책 필요 = 원본에서 먼저 결정
- 체크포인트: **Skill이 하네스에 없는 규칙을 만들지 않았는가**

## 8. 성숙도 평가 — 7축 × 4단계

축: 계약 · 기준 · 검증 · 경계 · 루프 · 기록 · 재사용
단계: **문서화 → 실행 가능 → 검증됨 → 강제됨**

| 축 | 내용 |
|---|---|
| 계약 | 실행 가능한 Issue 종료 조건 |
| 기준 | 질문별 SSOT와 충돌 처리 |
| 검증 | Local Verify와 결과 일치 |
| 경계 | 보호 영역과 Merge 권한의 실제 제한 |
| 루프 | 실패·중단·반려 후 다음 행동 정의 |
| 기록 | Issue 기반 새 세션 상태 복구 |
| 재사용 | 새 Issue에서도 재현 가능한 Skill 절차 |

미완성·후속 영역: Hook 이벤트 예약·백그라운드 실행 / 여러 Issue 병렬 오케스트레이션 / 비용·토큰 예산 관리 / 모델 성능 평가·자동 라우팅 / 조직 단위 승인 정책·감사 대시보드

**최종 통과 기준**: 실행 증거 9개 중 6개 이상 — 종료 조건이 명확한 Issue · Issue별 회귀 테스트 · verify PASS 기록 · 결함 FAIL 기록 · 독립 CI 결과 · LLM Review 결과 · 반려·재작업 기록 · 최종 승인·Merge 결과 · 원본 대조 Skill
